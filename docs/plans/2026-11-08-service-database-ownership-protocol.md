# Service Database Ownership Protocol

**Status:** Ownership protocol based on main `6f6197d`, extended through HOSTED-SERVER-038. The helper bootstrap handshake and migration-owner transfer are implemented; HOSTED-SERVER-026 through -032 route saved views, filter rules, triage queues, job inspection, and provider folders; HOSTED-SERVER-033 through -038 add account management, secret handoff, and detached-composer service routing. HOSTED-SERVER-039 moves persisted app UI state into a separate device database using a copy-only import. Account CRUD and credential editing remain API-backed, but the main desktop still opens the service database and constructs service-owned stores; full database separation remains incomplete.

The detached composer no longer opens `aerion.db`; `ComposerApp` requests these operations from its parent desktop process over authenticated IPC. ## Decision: separate service and desktop databases

Keep the current `aerion.db` as the service-owned authoritative mailbox database during the transition. `app_state` is the first extracted device-owned table in `device.db`; its first-run import copies rows idempotently and retains the old rows. Continue moving only clearly device-local state after its callers are identified. Do not give the desktop a writable handle to the service database as a permanent cache strategy. Service API results may populate a bounded, rebuildable presentation cache owned by the desktop.

The service database is migrated only by the helper binary. The desktop invokes the sibling helper's versioned `bootstrap` command before opening `aerion.db`, validates the bootstrap protocol, mailbox API version, and schema versions, and does not call `database.Migrate()`. Helper runtime startup, SMTP account transport, API-client administration, and bootstrap use the same ownership lock; account transport no longer migrates independently. Desktop, detached composer, and helper database users hold shared schema locks for their database lifetimes; a pending migration requires an exclusive lock. The helper pauses a running macOS LaunchAgent before a pending desktop-triggered upgrade and restores it afterward. On other platforms it refuses a pending upgrade when the default helper listener is active; manually managed services on custom ports must be stopped by the operator. This transfers schema migration ownership but does not yet remove desktop store construction or direct writes.

## Bootstrap and upgrade protocol

1. Package the helper beside the desktop in development and supported platform builds. Completed by HOSTED-SERVER-024.
2. Add helper bootstrap/health/version behavior and transfer migration ownership. HOSTED-SERVER-025 implements the versioned schema handshake, helper migration, active-process locks, and macOS LaunchAgent stop/restart around pending migrations. The desktop refuses an incompatible helper and does not fall back to desktop migrations.
3. Complete service API ownership of mailbox stores and writes. Until that work lands, the desktop still opens `aerion.db` under shared schema locks; only schema migration has one owner. The detached composer uses parent IPC for service-owned operations.
4. Preserve existing user data in place in `aerion.db`. HOSTED-SERVER-039 adds `device.db` for app UI state and performs an idempotent copy while retaining the legacy source. Add further desktop-only tables only after their callers and lifecycle requirements are verified.
5. Fail closed on a newer/unsupported service schema and show a repairable status. Do not silently fall back to opening the service database with desktop stores or run desktop migrations as a fallback.
6. Keep local-only platforms usable by packaging the helper there or by explicitly scoping the always-on service feature and migration owner to supported platforms. Do not claim the server split is complete on a platform that still has desktop-owned service migrations.

## API work required before the split

The service API needs account setup/update and credential handoff, provider folder discovery, saved-view/virtual-folder writes and cache rebuild, filter rule CRUD plus uncertain-job inspection/recovery, and draft/send operations with durable provider receipts and sent-message reconciliation. HOSTED-SERVER-033 specifies a dedicated `account.manage` capability because account changes transfer mailbox access and secrets, and defines one-time secret handoff with no secret-bearing reads. Triage/Reply Later list and mutation operations are routed through the helper, with Gmail hidden labels preserved where modify scope exists. Existing API work also covers mailbox reads, explicit body/attachment fetch, and actions. Each operation should move to the helper's existing shared store/use case; do not add duplicate frontend business logic.

The remaining implementation sequence is:

1. Move persisted mailbox workflow operations (views, filters, triage, drafts) to authenticated service APIs and route the desktop through them. HOSTED-SERVER-026 covers saved-view definitions, mutations, ordering, and cache refresh; HOSTED-SERVER-027 covers filter-rule CRUD/order; HOSTED-SERVER-029 covers Reply Later with Gmail labels and desktop Undo; HOSTED-SERVER-030 covers Read Later, Snooze, and service-owned expiry; HOSTED-SERVER-031 exposes uncertain filter jobs for bounded read-only inspection. Safe filter-job reconciliation and drafts/send remain.
2. Move account/folder setup and provider credential access behind the service boundary, including detached compose. HOSTED-SERVER-032 routes folder catalog reads, provider discovery, and subscription changes. HOSTED-SERVER-033 designs the account boundary; follow with HOSTED-SERVER-034 capability/consent, -035 account CRUD/lifecycle, -036 password/SMTP credential handoff, -037 OAuth/custom-provider/shared-mailbox handoff, and -038 detached-composer migration.
3. Move device-only stores to a desktop database and remove service-store construction from desktop processes. HOSTED-SERVER-039 begins this by extracting `app_state`; contacts, cryptographic metadata, device preferences, and the remaining service-store dependencies still need separate ownership decisions and migrations.
4. Verify upgrade, rollback refusal, concurrent launch, stopped service, first run, old-helper upgrade, manual-service recovery, and interruption recovery on every supported platform. Resolve custom-port manual-service detection and exercise the LaunchAgent upgrade lifecycle on a real macOS account.

Helper packaging and the versioned bootstrap/schema-owner cutover are implemented by HOSTED-SERVER-024 and HOSTED-SERVER-025. HOSTED-SERVER-026 through HOSTED-SERVER-032 move saved-view, filter-rule, triage, uncertain-job inspection, and provider-folder operations through the helper API. HOSTED-SERVER-033 documents the account API design; its implementation and detached-composer migration remain. Full server ownership is not complete: the desktop still constructs and writes other service-owned stores, and authenticated APIs for those operations remain required.
