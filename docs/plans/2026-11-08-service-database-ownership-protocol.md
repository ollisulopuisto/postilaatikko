# Service Database Ownership Protocol

**Status:** Ownership protocol based on main `6f6197d`, extended through HOSTED-SERVER-047. The helper bootstrap handshake and migration-owner transfer are implemented; HOSTED-SERVER-026 through -038 route persisted mailbox workflows, account/credential changes, and detached-composer service operations. HOSTED-SERVER-039 moves persisted app UI state to `device.db`; HOSTED-SERVER-043 moves desktop preferences and the image-loading allowlist there; HOSTED-SERVER-044 moves explicit folder body-prefetch choices there; HOSTED-SERVER-045 moves desktop TLS trust-on-first-use decisions there. These device imports are copy-only. HOSTED-SERVER-040 hardens matched thread reads, and -041/-042 close mailbox-list and mutation consistency gaps. HOSTED-SERVER-046 moves connected virtual-folder search and cached result reads into the helper, which refreshes saved-view caches while the desktop is closed. HOSTED-SERVER-047 lets the desktop connect to a user-operated HTTPS helper with a per-device token stored in the OS keyring, using normal TLS validation and the helper's Host allowlist. The desktop still opens a local service database and has local-store fallbacks for unmigrated workflows; a remote-only desktop startup is not yet supported. Contacts/CardDAV, S/MIME and PGP stores remain under review, so full database separation is incomplete.

## Decision: separate service and desktop databases

Keep the current `aerion.db` as the service-owned authoritative mailbox database during the transition. `app_state`, desktop `settings`, `image_allowlist`, `folder_content_policies`, and desktop `trusted_certificates` are extracted device-owned tables in `device.db`; imports are idempotent and retain the source rows. The helper's scheduled-send certificate store remains service-owned. Virtual-folder membership caches are service-owned and rebuilt by helper maintenance; API cache results are bounded to 200 conversations and hydrate current row state. Continue moving only clearly device-local state after its callers are identified. Do not give the desktop a writable handle to the service database as a permanent cache strategy. Other service API results may populate a bounded, rebuildable presentation cache owned by the desktop.

The service database is migrated only by the helper binary. The desktop invokes the sibling helper's versioned `bootstrap` command before opening `aerion.db`, validates the bootstrap protocol, mailbox API version, and schema versions, and does not call `database.Migrate()`. Helper runtime startup, SMTP account transport, API-client administration, and bootstrap use the same ownership lock; account transport no longer migrates independently. Desktop, detached composer, and helper database users hold shared schema locks for their database lifetimes; a pending migration requires an exclusive lock. The helper pauses a running macOS LaunchAgent before a pending desktop-triggered upgrade and restores it afterward. On other platforms it refuses a pending upgrade when the default helper listener is active; manually managed services on custom ports must be stopped by the operator. This transfers schema migration ownership but does not yet remove desktop store construction or direct writes.

## Bootstrap and upgrade protocol

1. Package the helper beside the desktop in development and supported platform builds. Completed by HOSTED-SERVER-024.
2. Add helper bootstrap/health/version behavior and transfer migration ownership. HOSTED-SERVER-025 implements the versioned schema handshake, helper migration, active-process locks, and macOS LaunchAgent stop/restart around pending migrations. The desktop refuses an incompatible helper and does not fall back to desktop migrations.
3. Complete service API ownership of mailbox stores and writes. Until that work lands, the desktop still opens `aerion.db` under shared schema locks; only schema migration has one owner. The detached composer uses parent IPC for service-owned operations.
4. Preserve existing user data in place in `aerion.db`. HOSTED-SERVER-039 adds `device.db` for app UI state and performs an idempotent copy while retaining the legacy source. Add further desktop-only tables only after their callers and lifecycle requirements are verified.
5. Fail closed on a newer/unsupported service schema and show a repairable status. Do not silently fall back to opening the service database with desktop stores or run desktop migrations as a fallback.
6. Keep local-only platforms usable by packaging the helper there or by explicitly scoping the always-on service feature and migration owner to supported platforms. Do not claim the server split is complete on a platform that still has desktop-owned service migrations.

## API work required before the split

The service API now covers account setup/update and credential handoff, provider folder discovery, saved-view writes/cache refresh and cached-result reads, filter-rule CRUD plus uncertain-job inspection, triage queues, virtual-folder search, mailbox reads, explicit body/attachment fetch, actions, draft CRUD/reply preparation, prepared immediate send, and durable send-receipt lookup. HOSTED-SERVER-033 specifies a dedicated `account.manage` capability because account changes transfer mailbox access and secrets, and defines one-time secret handoff with no secret-bearing reads. Triage/Reply Later operations route through the helper, with Gmail hidden labels preserved where modify scope exists. Remaining ownership work includes normal desktop compose/draft synchronization, direct local fallback/store access, derived virtual-folder unread counts, and safe uncertain-job reconciliation. Each operation should move to the helper's existing shared store/use case; do not add duplicate frontend business logic.
